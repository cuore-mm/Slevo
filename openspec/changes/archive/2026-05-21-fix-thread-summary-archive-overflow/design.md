## Context

板更新では subject.txt の取得結果を `thread_summaries` に反映し、ローカルに存在するが最新 subject.txt に存在しないスレッドを `isArchived = 1` に更新している。現在の差分計算は当該板の `thread_summaries` 全件を既存 ID として扱うため、既にアーカイブ済みの過去スレッドも毎回アーカイブ対象に含まれる。

Room は `List<String>` を `IN (:threadIds)` の SQL 変数へ展開する。過去スレッドが蓄積した板では `threadIds` が SQLite の変数上限を超え、`too many SQL variables` によりトランザクション全体が失敗する。失敗後も DB 内の蓄積状態は変わらないため、再起動しても同じ更新失敗が再現する。

## Goals / Non-Goals

**Goals:**
- 板更新時にアーカイブ対象 ID が大量になっても SQLite の変数上限を超えない。
- 既にアーカイブ済みのスレッドを再アーカイブ対象から除外し、不要な更新量を抑える。
- subject.txt に再出現したスレッドは現役スレッドとして復帰し、タイトル・レス数・順位を更新する。
- 大量の過去スレッドが蓄積済みの既存 DB でも、追加の手動復旧なしに板更新できる。

**Non-Goals:**
- `thread_summaries` のスキーマ変更やデータ削除ポリシーの追加は行わない。
- 板更新 UI のエラー表示設計はこの変更では扱わない。
- 共通客観状態の GC 仕様は変更しない。

## Decisions

### 1. 差分計算の既存 ID は未アーカイブに限定する

`removed` の母集合は、対象板の `isArchived = 0` のスレッド ID に限定する。これにより、既に過去スレッドとして扱われた行を毎回 `removed` に含めず、通常更新時のアーカイブ対象を「今回 subject.txt から消えた現役スレッド」に絞る。

代替案として、全件取得を維持したまま `markArchived` 側だけを分割する方法もある。この方法でも SQL 変数上限は回避できるが、アーカイブ済み行を毎回更新対象にし続けるため、既存 DB の蓄積に比例して更新時間が増え続ける。差分計算の入力を正す方が、現象の再発抑止として適切である。

### 2. アーカイブ更新は安全なチャンク単位で実行する

未アーカイブに限定しても、板の subject.txt が大きく変化した場合や初回復旧時にはアーカイブ対象が多くなる可能性がある。DAO 呼び出し側で固定上限以下のチャンクに分割し、1 回の SQL に渡す変数数を SQLite の上限より十分小さくする。

チャンクサイズは `boardId` の変数 1 件を含めても余裕がある値にする。実装では定数化し、テストが想定件数を明示できるようにする。

代替案として、SQL を `WHERE boardId = :boardId AND isArchived = 0 AND threadId NOT IN (:currentIds)` のように現在 subject.txt 側を渡す形にする案がある。ただし subject.txt の現役スレッド数も大量になる可能性があり、同じ変数上限問題を別方向で踏む。今回の修正では、現行構造を保ちながら安全な分割を行う。

### 3. 復活スレッドは既存更新経路で未アーカイブ化する

subject.txt に含まれる ID が既存行にある場合、既存更新処理で `isArchived = 0` に戻す。差分計算を未アーカイブに限定しても、復活スレッドは `existingIds` 判定または挿入競合処理で正しく扱う必要がある。

既存行判定まで未アーカイブ限定にしてしまうと、アーカイブ済み行を新規挿入しようとして主キー競合により更新されない可能性がある。そのため、設計上は「存在判定」と「アーカイブ対象抽出」を分離する。

## Risks / Trade-offs

- [Risk] 存在判定まで未アーカイブ限定にすると、過去スレッドの復活時に更新されない。 → 存在判定用の ID とアーカイブ対象抽出用の ID を分け、復活ケースをテストに含める。
- [Risk] チャンクサイズが大きすぎると端末や SQLite バージョンによって再び上限を超える。 → 余裕のある固定値を使い、`boardId` 分も考慮する。
- [Risk] 複数チャンク更新の途中で失敗すると一部だけ反映される。 → 既存の板更新トランザクション内で実行し、失敗時は全体をロールバックする。
- [Risk] 大量更新のテストが遅くなる。 → DAO または Repository の最小限の単体テストで件数境界を確認し、UI テストには持ち込まない。

## Migration Plan

スキーマ変更は不要。既存 DB に大量のアーカイブ済みスレッドが残っていても、次回板更新では未アーカイブのみをアーカイブ対象にするため、追加のデータ移行なしに回復できる。

ロールバック時は、以前の全件差分計算と一括 `IN` 更新に戻るため、同じ DB 状態で再び更新不能になる可能性がある。リリース後は板更新失敗ログに `too many SQL variables` が残っていないことを確認する。

## Open Questions

- 板更新失敗を UI に表示するかどうかは別変更で検討する。
- 長期的に `thread_summaries` のアーカイブ済み行を GC するかどうかは別仕様で検討する。
