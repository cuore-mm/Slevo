## Why

板更新時に `thread_summaries` のアーカイブ対象スレッド ID が大量になると、Room が `IN (:threadIds)` を多数の SQL 変数へ展開し、SQLite の変数上限を超えて更新が失敗する。失敗後もアーカイブ済みを含む過去スレッドが再び対象になり続けるため、アプリ再起動後も同じ板を更新できない状態が継続する。

## What Changes

- 板更新時のスレッド一覧キャッシュ差分計算で、既にアーカイブ済みのスレッドを再アーカイブ対象に含めない。
- アーカイブ対象が多数でも SQLite の変数上限を超えないよう、DAO 呼び出しまたは更新処理を安全な単位に分割する。
- 板更新中にアーカイブ処理が失敗した場合でも原因を追跡できるよう、失敗の扱いと観測ポイントを整理する。
- 既存 DB に過去スレッドが大量に蓄積している状態でも、次回以降の板更新が成功できることを確認するテスト観点を追加する。

## Capabilities

### New Capabilities
- `board-thread-refresh-cache`: 板更新時に subject.txt とローカルのスレッド一覧キャッシュを照合し、現役スレッドの更新・新規追加・過去スレッドのアーカイブを安全に完了する振る舞いを定義する。

### Modified Capabilities
- `thread-state-sync`: 板更新が共通客観状態へ最新レス数を保存する際、スレッド一覧キャッシュの大量アーカイブ処理に阻害されず同期が完了する要件を追加する。

## Impact

- 影響範囲: `BoardRepository.refreshThreadList`、`ThreadSummaryDao`、`ThreadSummaryEntity` を中心とする板一覧キャッシュ更新経路。
- DB スキーマ変更は想定しない。
- 外部 API や通信仕様の変更は想定しない。
- テストでは、大量の過去スレッド ID を含む板更新ケースと、既存の通常更新・新規追加・復活スレッド更新ケースを確認する。
