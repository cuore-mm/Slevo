## Context

現在のレスポップアップは `PopupInfo.posts` に `ThreadPostUiModel` のリストを保持し、描画時に最新の `posts` から `indexOf(p)` で投稿位置を再探索している。スレッド更新では `applyLoadSuccess()` により投稿 UI モデルのリストと `idIndexList` などの派生情報が再生成されるため、ポップアップが持つ投稿オブジェクトが最新リスト上で見つからなくなる場合がある。

`ThreadPostUiModel` は `data class` であり、本文が同じ投稿でも `meta.momentum` や `meta.urlFlags` などの表示補助情報が変化すると等価ではなくなる。その状態で `idIndexList[postIndex]` を参照すると、`postIndex == -1` によりクラッシュする。レスポップアップの表示対象はスレッド内で安定している投稿番号で表現し、表示時に最新 UI 状態へ解決する設計へ変更する。

## Goals / Non-Goals

**Goals:**
- ポップアップ表示対象を投稿番号で保持し、スレッド更新後も最新の投稿 UI モデルへ解決する。
- `indexOf()` による古い投稿モデル照合をポップアップ描画経路から排除する。
- `idIndexList`、返信元、ID 集計、NG 状態、my 投稿状態など、投稿番号に紐づく派生情報を範囲外アクセスなしで取得する。
- レス番号、返信元、ID、ツリー、多段ポップアップ、画像 shared transition の既存挙動を維持する。
- 更新後に対象投稿が存在しない場合でもクラッシュせず、表示可能な投稿のみを描画する。

**Non-Goals:**
- dat 取得、差分更新、パーサー、永続化スキーマは変更しない。
- 投稿番号そのものが変化するスレッド再構成や削除仕様は新設しない。
- ポップアップ UI の見た目や配置アルゴリズムは、今回の安定化に必要な範囲を除いて変更しない。

## Decisions

### 1. `PopupInfo` は投稿 UI モデルではなく投稿番号を保持する

`PopupInfo.posts: List<ThreadPostUiModel>` を投稿番号リストへ置き換える。候補名は `postNumbers: List<Int>` とする。`indentLevels` と `rootNumbers` は現在どおりポップアップ内表示順に対応するリストとして扱う。

代替案として、スレッド更新時に `popupStack` 内の `posts` を最新インスタンスへ同期する方法がある。しかし、この方法は同期時にも等価比較へ依存し、表示補助情報の変化で対象投稿を落とす可能性が残る。投稿番号はレスポップアップ操作の入力にも使われており、ポップアップ表示対象の安定 ID としてより適切である。

### 2. ポップアップ描画時に投稿番号から最新投稿を解決する

`PopupPostLazyColumn` は `info.postNumbers` を走査し、各 `postNumber` に対して `posts.getOrNull(postNumber - 1)` を使って最新の `ThreadPostUiModel` を取得する。取得できない投稿番号は描画対象から除外する。これにより、スレッド更新で UI モデルが再生成されても、ポップアップは最新の本文・ヘッダー・メタ情報を表示する。

描画前に `postNumbers` と `posts` から表示可能な行モデルを組み立てると、`itemsIndexed` 内の早期 return と divider 表示条件のずれを避けやすい。行モデルには投稿番号、投稿 UI モデル、ポップアップ内インデックス、インデント情報を含める。

### 3. 投稿番号に紐づく派生情報は安全取得に統一する

`idIndexList` は `postIndex = postNumber - 1` を使い、`getOrElse(postIndex) { 1 }` で取得する。`replySourceMap[postNumber]`、`myPostNumbers`、`ngPostNumbers`、`idCountMap[post.header.id]` は投稿番号または最新投稿から取得し、範囲外添字参照を避ける。

NG 投稿は、ポップアップ作成時と同様に描画時にも除外する。スレッド更新または NG 状態変更により対象が表示不能になった場合、該当行を描画しない。すべての行が表示不能になった場合は、ポップアップコンテンツを空にせず、上位でポップアップを閉じるか描画をスキップする方針を実装時に選択する。

### 4. ポップアップ作成処理は対象投稿番号を正本にする

`addPopupForReplyNumber` は単一の投稿番号、`addPopupForReplyFrom` は返信番号リスト、`addPopupForId` は ID に一致した投稿番号リスト、`addPopupForTree` はツリー選択結果の投稿番号リストを `PopupInfo` に渡す。対象投稿の存在確認と NG 除外は引き続き ViewModel 側で行い、ポップアップ作成時に空の場合は追加しない。

連続同一ポップアップの抑止は、投稿 UI モデルのリスト比較ではなく、投稿番号リスト、インデント、ルート番号の比較に変更する。これにより、スレッド更新で UI モデルが再生成されても同一内容判定が安定する。

### 5. shared transition と多段ポップアップは投稿番号をそのまま利用する

画像 shared transition の popup namespace は既に `popupId` と `postNumber` で構成されているため、投稿番号保持へ変更しても識別規則は維持できる。多段ポップアップの表示基準座標は、描画された投稿行の座標測定結果を使う現行方針を維持する。

## Risks / Trade-offs

- [Risk] スレッド更新や NG 状態変更で、ポップアップ作成時に存在した投稿が描画時に解決できなくなる。 → 投稿番号解決に失敗した行はスキップし、空ポップアップを表示しない処理を追加する。
- [Risk] `indentLevels` / `rootNumbers` と表示可能行の対応が、NG 除外や範囲外除外でずれる。 → ポップアップ作成時の順序インデックスを保持した行モデルを組み立て、インデント取得は元のポップアップ内順序に対応させる。
- [Risk] `PopupInfo` の構造変更によりテストデータや Preview が壊れる。 → `PopupInfo` を生成するテスト・Preview を投稿番号ベースへ更新し、既存のポップアップ表示テストを回帰確認する。
- [Risk] 投稿番号リストだけでは表示内容のスナップショット性が失われ、更新後の最新内容がポップアップに表示される。 → 今回の目的はクラッシュ回避と最新状態への安全な追従であり、レスポップアップはスレッド画面の現在状態を反映する契約として扱う。
