## Context

Issue 490 では、スレッド画面で自動スクロールを有効にした状態でタブ切り替えまたは他画面遷移を行うと、復帰時にスクロール位置が画面を離れた瞬間ではなく数秒前の位置へ戻る。

現在のスクロール位置保存は `BbsRouteScaffold` が `LazyListState.firstVisibleItemIndex` と `firstVisibleItemScrollOffset` を `snapshotFlow` で監視し、`debounce(200L)` 後に ViewModel 経由でタブ固有状態へ保存している。自動スクロール中は `scrollBy()` による位置更新が継続するため、`debounce` は「最後の更新から 200ms 静止した状態」を待ち続け、離脱直前の値が保存されない。

また、スレッド投稿行の LazyColumn key は行インデックスを含むため、投稿一覧の表示順が変わると key が変化し、Compose のスクロール位置維持が不安定になり得る。一方で、ツリー表示や新着境界の文脈表示では同じレス番号の投稿が通常行と dimmed 行として複数回現れるため、レス番号単独の key にはできない。

## Goals / Non-Goals

**Goals:**

- 自動スクロール中でも保存済みスクロール位置が継続的に最新化される。
- タブ切り替え、画面遷移、Composable 破棄時に、その時点のスクロール位置を保存する。
- 手動スクロール時の既存復元挙動を維持する。
- スレッド投稿行の key を行インデックス非依存にし、同一レス番号の複数表示も一意に識別できる形で安定化する。
- DB スキーマ変更なしで Issue 490 を解消する。

**Non-Goals:**

- レス番号を正本とする新しいスクロールアンカー永続化は本変更では扱わない。
- NG フィルタ、検索、ツリー表示切り替えをまたいだ完全なレス番号ベース復元は本変更では扱わない。
- 自動スクロール速度や下端更新ロジックは変更しない。
- タブ状態や履歴状態のデータモデル再設計は行わない。

## Decisions

### 1. `debounce` ではなく定期保存で連続スクロールを扱う

スクロール位置監視は、連続更新が止まるまで待つ `debounce` ではなく、連続更新中も一定間隔で最新値を保存する方式に変更する。候補は `sample` または同等の throttle 実装とし、保存頻度は既存の 200ms 程度を基準にする。

代替案として保存のたびに即時書き込みする方法もあるが、自動スクロール中はフレーム単位で値が変わるため、DB 更新や Flow 再通知が過剰になる。定期保存は復元精度と更新負荷のバランスを取れる。

### 2. 画面離脱時に現在位置を即時保存する

定期保存だけでは、最後の保存直後から画面を離れるまでの差分が残る可能性がある。タブが非アクティブになる時点、または該当ページの Composable が破棄される時点で、`LazyListState` の現在値を同期的に読み取り、既存の `updateScrollPosition` 経路へ渡す。

この処理により、通常のタブ切り替え、スワイプによるページ変更、別画面への遷移、ナビゲーションスタックからの離脱で最終位置を保存できる。

### 3. 保存経路は既存の ViewModel / Repository 経路を維持する

スクロール位置の保存先は既存の `ThreadTabInfo.firstVisibleItemIndex` と `firstVisibleItemScrollOffset` のままとし、`ThreadViewModel.updateThreadScrollPosition`、`ThreadTabCoordinator.updateThreadScrollPosition`、`TabsRepository.saveOpenThreadTabs` の経路を維持する。

DB スキーマを変更しないため、移行処理や既存データ変換は不要になる。Issue 490 の直接原因は保存タイミングであり、保存形式の変更は後続改善として分離する。

### 4. スレッド投稿行 key はレス番号と表示上の役割を組み合わせる

`buildThreadListItemKey` は行インデックスを使わず、投稿の安定識別子であるレス番号と、その行が通常表示か文脈表示かを表す表示上の役割を組み合わせて生成する。候補は `num`、`dimmed`、`isAfter`、`depth` など、表示順に依存せず同一レス番号の複数表示を区別できる `DisplayPost` の安定プロパティである。

レス番号単独の key は採用しない。ツリー表示では新着側の子レスを見せるために親レスが dimmed 行として再挿入されることがあり、同じレス番号が複数回表示される。key は Compose の要件でリスト内一意である必要があるため、レス番号を中心にしつつ、通常行・dimmed 行・新着側文脈行・ツリー深さなどの役割差分で一意性を担保する。

## Risks / Trade-offs

- [Risk] 定期保存の頻度が高すぎると DB 更新が増える。 → `distinctUntilChanged` と 200ms 程度の間隔で不要更新を抑制する。
- [Risk] 画面離脱時保存と定期保存が近接して同じ値を二重保存する。 → 保存値の重複抑制、または同じ値を保存しても副作用が小さい既存経路を利用する。
- [Risk] `sample` 相当の処理では、最終イベントが次の周期前に失われる。 → 離脱時即時保存を併用して最終位置を補完する。
- [Risk] レス番号単独 key にするとツリー表示や文脈表示で重複する。 → レス番号に `dimmed`、`isAfter`、`depth` などの表示役割を加え、行インデックスなしで一意性を確認するテストを追加する。
- [Risk] 汎用 `BbsRouteScaffold` の変更が板画面にも影響する。 → 手動スクロール、タブ切り替え、復元の既存挙動を板・スレッド双方で確認する。
