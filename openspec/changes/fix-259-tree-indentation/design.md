## Context

現在のツリー表示は段数ごとに固定のインデント増分（16dp）を適用しており、深いツリーでは本文領域が過度に圧縮される。
Issue #259 では「通常レス横幅の 1/4 をインデント最大値にする」ことと、「最深段が上限を超える場合に増分を自動調整する」ことが要求される。
本変更はスレッド本体リストとツリーポップアップの双方に同一契約で適用し、表示の一貫性を保つ必要がある。

## Goals / Non-Goals

**Goals:**
- ツリーごとの最深段に応じてインデント増分を動的に算出し、合計インデントを通常レス横幅の 1/4 以内に制約する。
- 浅いツリーでは既存の見た目（16dp 増分）を維持し、必要時のみ縮小を適用する。
- 本体リストとツリーポップアップで同一のインデント計算を適用する。
- 計算ロジックを純粋関数として分離し、境界値をユニットテストで固定化する。

**Non-Goals:**
- ツリー深さ算出ロジック（親子判定や DFS 順序）の変更。
- ツリー表示以外（NUMBER 表示や他画面）の余白ルール変更。
- フォントサイズや行間など、インデント以外の可読性調整。

## Decisions

- **インデント幅を「段数」ではなく「実幅(Dp)」で扱う**
  - これにより段数依存の固定増分から、上限付き可変増分へ移行できる。
  - 代替案として段数のまま倍率補正を各描画箇所で実施する方法があるが、重複計算と適用漏れリスクが高いため採用しない。

- **ツリー単位の最大深さから増分を算出する**
  - `step = min(defaultStep, maxIndent / maxDepth)` の形で増分を決定し、`depth * step` を各行に適用する。
  - `maxDepth` が 0 の場合は 0dp を返し、単独ルートでは追加インデントを発生させない。
  - 代替案として全体固定上限のみを導入する方法があるが、ツリーごとの深さ差を吸収できず浅いツリーまで不必要に詰まるため採用しない。

- **通常レス横幅の 1/4 を上限値として算出する**
  - 横幅は実測可能なコンテナ幅から計算し、端末幅差を自然に吸収する。
  - 測定前フォールバック時は既存固定増分を優先し、計測後に上限契約へ収束させる。

- **区切り線(HorizontalDivider)も同一インデント計算を使用する**
  - 行本体と区切り線で異なる計算を使うと視覚的なズレが生じるため、同じ実幅計算を適用する。

## Risks / Trade-offs

- [Risk] 横幅計測タイミングによって初期描画と再描画でインデントが変化し、瞬間的に揺れる可能性がある。
  - Mitigation: フォールバック戦略を明示し、計測後のみ更新する経路に限定する。

- [Risk] 端末幅が極端に狭い場合、1/4 制約で増分が小さくなりツリー構造が視認しづらくなる可能性がある。
  - Mitigation: 最小可読幅の下限値を導入するかは今回の観測項目として扱い、初回は Issue 要件を優先して 1/4 制約を厳密適用する。

- [Trade-off] 描画コンテナ幅への依存が増えるため、インデント計算の入力が増える。
  - Mitigation: 幅入力を受け取る専用ヘルパーに集約し、UI 側は結果適用だけにする。
